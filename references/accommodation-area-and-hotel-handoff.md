# 住宿区域研究与酒店搜索交接

这套流程把行程转换成可执行的住宿分段和 TourMind 酒店搜索输入。目标是先选对区域，再获取实时酒店；不是先列热门酒店，也不是让酒店搜索反过来破坏已确认的路线。

进入查询前读取 [机酒补充与 Journal 衔接](../playbooks/service-to-journal.md)。采集、推荐与暂选都应说明怎么接回 Travel Journal；酒店工具的报价或预订提示不能成为整轮对话的终点。

## 内容

## 触发与顺序

用户明确询问住哪里、换不换酒店或附近酒店，接受排日程阶段的酒店推荐邀请，或在路线就绪时选择先补酒店、交付后接受尚未询问过的酒店补全邀请时执行。目的地内主题路线不因为“两天”“多日”自动进入查询；第一批具体日程后可轻问一次，用户接受才执行，已有住处、拒绝或暂缓不重复问；选择先生成 Travel Journal 时不执行：

1. 从当前旅程真值生成住宿分段，按 [输入继承与估算](intake-contract.md#机酒输入的继承与估算) 复用日期、天数和同行者，先推导暂估退房日与已知配置；
2. 搜索并比较 2–3 个区域，给出一个主选和最多一个条件式备选；
3. 回显主选区域、晚数与入住配置及必要的暂估依据，只合并询问无法从前文推导的搜索必需项。用户已要求按路线推荐时，区域由路线判断，不额外要求确认区域才搜索；
4. 主选区域确定且位置、入住、退房、每房成人数、房间数已按继承与估算规则补齐后，立即调用 `tourmind-booking`，不再追问用户是否需要查询；
5. 用户暂选酒店后把它写回路线锚点并衔接 Journal：执行已有的后续要求，或给生成入口并轻提尚适用、未询问过的可选航班；不止于“已记入行程”。创建订单与付款继续遵守独立确认门槛。

酒店实时搜索是路线规划的一部分，可以在最终行程确认前完成。餐厅席位、活动余票和酒店下单仍不得阻塞 JourniOne 第一阶段交付。
查询前读取 [tourmind-query-dependency.md](tourmind-query-dependency.md)。无 Token 时直接使用公开 ToC HTTPS 查询，不能把缺少凭证或额外 MCP 当成不可用。确实缺少 `tourmind-booking` 或宿主 HTTPS 能力时返回完整住宿搜索包和缺失能力说明，不用普通网页结果冒充实时酒店。
区域确认不是第二次授权门槛：一旦搜索必需输入齐全，实时酒店推荐就是规划流程的下一步。若住宿段不止一个，分别调用并各自只返回一个首选。

用户在分叉中选择“酒店和往返航班”时，两项查询均已获授权；只选择酒店时不得顺带询问出发地、机场或机票状态。用户选择先生成 Travel Journal 或明确不需要酒店时，不生成住宿搜索包，不把人数、日期或房间列为 Travel Journal 的待确认项。

## 住宿分段

每次都从行程推导，不沿用可能过时的旧结论：

- 同一城市连续住宿合并为一段；
- `check_in` 是进入该住宿地的日期，`check_out` 是离开的日期，晚数由两者确定；
- 记录到达站/机场、离开站/机场、逐日首末主节点、固定早晚活动、行李步骤；
- 记录总成人数、儿童人数与年龄、房间数、每房成人数和无障碍/床型需求；
- 用户已选或已订酒店时标为固定锚点，不参与自动替换。

当前 TourMind 的 `adults` 表示每房成人数。沿用已知房间分配；夫妻两位成人可按采集契约明示暂按一间查询。其他只知道总人数、多人多房分配不明或不均时，先补缺失配置；不要把儿童擅自计为成人，也不要假设所有房间入住人数相同。

## 区域经验搜索

先计算路线适配，再补充居住体验：

1. **动线**：逐日首末节点、跨城方向、固定晚间活动和机场接驳是否减少折返与换乘；
2. **行李**：抵达、退房、寄存、回酒店取行李和进站是否顺路；
3. **同行者**：父母关注电梯、坡度、安静、座位与医院/药店；孩子关注午睡、婴儿车、便利店与家庭房；情侣关注咖啡、晚餐、散步和夜间氛围；
4. **居住体验**：夜间噪声、晚餐选择、清晨便利、街区氛围和安全感；
5. **换酒店成本**：只有多日路线明显受益或城市实际改变时才增加换店；不为单个景点制造一晚搬家。

交通、车站结构、坡度和营业事实用官方交通、地图或一手页面核实。近期社区、论坛和旅行者内容只能支持“较安静”“夜间热闹”等经验判断；至少交叉查看两个独立近期来源，并标明主观性。酒店本身的图片、坐标、设施、房型、价格、取消和库存只采用 TourMind 数据。

## 区域结果

默认简洁返回：

```text
住宿段：<城市>｜<check_in> 至 <check_out>｜<nights> 晚
入住：<总人数>｜<room_count> 间｜每房 <adults_per_room> 位成人
主选区域：<区域>
搜索中心：<完整 POI/车站/商圈名称 + 城市国家>
选择理由：<与实际路线对应的 2–3 条>
体验取舍：<安静/热闹、餐饮、坡度、亲子或长辈便利>
条件式备选：<只有明确取舍时提供>
来源与核验日期：<事实来源 + 经验来源>
状态：区域已选 | 入住配置待确认 | 可查询实时酒店
```

不要只写“交通方便”。理由必须指向当前行程，例如“抵达乘 HARUKA、离开从京都站前往大阪，两次携带行李均不换乘”。

## TourMind 住宿搜索包

区域结果确认后生成：

```yaml
segment_id: stay-01
trip_version: <当前旅程真值版本>
city_country: <城市, 国家>
check_in_date: YYYY-MM-DD
check_out_date: YYYY-MM-DD
night_count: <整数>
location:
  query: <完整区域/车站/POI 名称>
  mode: poi | region
  radius_km: <用户明确值；否则留给 TourMind recommended_radius_km>
occupancy:
  total_adults: <整数>
  children_per_room: <整数；没有儿童时为 0>
  children_ages_per_room: [<本房每名儿童年龄；无儿童时为空>]
  room_count: <整数>
  adults_per_room: <整数或待确认>
hard_constraints:
  budget: <金额、币种、每晚或全程；未提供则留空>
  star_rating: <未提供则留空>
  radius_km: <用户明确时才是硬约束>
  facilities: []
soft_preferences:
  - <早餐、安静、电梯、双床、免费取消等>
route_context:
  arrival_anchor: <名称>
  departure_anchor: <名称>
  daily_anchors: [<名称>]
  fixed_events: [<名称与时间>]
```

把 `location.query` 作为 `keyword` 交给 TourMind `search_location`。区域住宿先检查准确匹配的 `data.regions`；车站、入口或明确半径使用 `data.place`、其 `recommended_radius_km` 和 `search_scope`，不要自行猜坐标。链接存在时保留 `data.web_url` 及同层有效期字段，缺失则省略，不索取 Token 补链接。预算先按查询依赖契约转换为 CNY 全程全部房间总额；展示仍采用 Journal 已确定币种。将每房字段映射为 `adults`、`children`、`children_ages`；分配不均时按已确认的各入住配置分别查询，不把总人数填入每房字段。

## 首选展示与候选缓存

TourMind 的检索与核验逻辑遵循当前官方版本：保留完整原始候选池，多个候选用 `batch_query_room_rates`（每批最多 20 家、最多同时 3 批），单店用 `query_room_rates`，对所有进入排名的酒店核验实时房型，选出最多 5 家。JourniOne 只改变用户看到结果的节奏：

1. 每个住宿段首次只展示排名第一的首选酒店；
2. 返回首选名称、图片、距离、星级、对应入住配置的实时房型、每晚与全程价格、餐食、取消政策、库存状态、地址，以及两三条可验证的匹配理由；
3. 多人多房且入住人数不均时，首选必须同时存在每一种入住配置的匹配产品；分别显示价格与政策，并给出房间合计；
4. 首次回复可以返回首选酒店的 `query_room_rates.data.web_url` 或成功批量项的 `data.web_url`，不得返回会直接暴露全部候选的 `search_hotels.data.web_url`；没有单店链接时省略；
5. 不展示其余四家名称，也不把它们写进“顺便看看”或对比表；只用一句话说明“另有已核验备选，需要时可以展开”。

首次回复保持紧凑：

```markdown
### 住宿首选｜<住宿段>

**<酒店名称>** · <距离> · <星级>

- 房型与入住：<按每种入住配置分别列出>
- 价格：<每晚 / 全程 / 多房合计 / 币种>
- 取消与库存：<原样政策 / 立即可订或需确认>
- 为什么选它：<两三条已验证理由>
- 查看房型与实时报价：<首选酒店房型响应的 data.web_url；没有则省略>

另有 <实际缓存数量> 家已核验备选，需要时可以换。
这家合适的话可以先放进行程，接着就能把每天的安排做成 Travel Journal；想换住处也可以。
```

当前任务缓存按住宿段保存：

```yaml
hotel_result_cache:
  segment_id: <住宿段>
  trip_version: <旅程真值版本>
  channel: toc | tob
  search_fingerprint: <通道、位置、半径、日期、每房成人和儿童年龄、房间数与硬约束>
  verified_at: <时间与时区>
  primary_hotel_id: <首选>
  hidden_alternatives:
    - rank: 2
      hotel_id: <TourMind hotel_id>
      match_summary: <仅内部>
      live_rate_snapshot: <房型、价格、政策、库存与核验时间>
  search_view_urls: <TourMind 原样 URL，仅内部缓存>
  status: current | quote_stale | invalid
```

缓存仅代表当前任务的已核验结果，不承诺跨会话持久化。用户追问时：

- “更多选择、还有吗、换一家” → 按缓存排名返回其余候选，默认最多 4 家；
- “便宜一点、近一点、必须无烟”等 → 在缓存候选中按新偏好重排；新要求成为硬约束且缓存无法验证时补查详情或重新搜索；
- 追问发生在同一任务且搜索指纹未变 → 可以展示缓存候选，但价格必须保留原核验时间；
- 用户只说“暂时选这家” → 保存已展示选择与报价时间，接回 Journal，不为暂选重新查价；不把暂选解释成准备下单；
- 用户要求“现在的价格”、明确准备下单，或需要使用的临时链接/报价已失效 → 重新调用 `query_room_rates`，不要把快照冒充当前报价；
- 用户只问首选的房型、图片或政策 → 查询并展开首选，不自动释放其余四家。

## 行程变化与失效

以下变化只重算受影响住宿段：

- 日期或城市变化 → 更新入住、退房、晚数，旧实时房价与库存全部失效；
- ToC/ToB 通道变化 → 旧报价、rate_code、政策与库存失效，在新通道重新查价并验价；订单操作仍使用创建通道；
- 逐日首末节点、固定晚间活动或机场变化 → 重新比较区域；
- 同行人数、儿童年龄、房间数或每房人数变化 → 旧房型与报价失效；
- 位置、半径、日期、入住配置或硬约束变化 → `search_fingerprint` 改变，整段候选缓存失效并重新搜索；
- 只有排序偏好变化且缓存字段足以判断 → 保留候选身份并重排；涉及当前价格时仍重新核价；
- 用户选定酒店 → 使用 TourMind 返回坐标作为内部路线锚点；
- 用户已预订酒店 → 优先调整路线适配酒店，除非用户同意换店。

每次变化回显“原住宿段 → 新住宿段”和失效内容。不要静默保留旧价格，也不要因一个景点变化自动更换区域。
选定酒店导致逐日首末动线变化时，更新 Overview、交通与地图锚点，并重新让用户确认受影响行程；不要让酒店版本与 JourniOne 版本分叉。

具体酒店默认只用于内部动线和酒店搜索。JourniOne 分享页与公开 Google Maps 默认展示住宿区域锚点；只有用户知情同意后才公开具体酒店名称与坐标。
