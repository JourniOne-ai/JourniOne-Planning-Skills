# 行程展示契约

这套格式用于未来行程的初稿、完整修改稿和确认后交付。目标是让用户先看懂全程节奏，再阅读每天时间线；研究过程、餐厅证据和个性化提醒不得挤进主行程。

首次规划按 [分步规划](../playbooks/progressive-planning.md) 展示。兴趣选择后的下一份回复包含全程 Overview 与首批具体建议时间线，逐步补齐全部天次；资料足够时直接展示全程。地图与研究说明不阻塞首批日程，完整时间表必须在生成 Journal 前已可阅读修改。兴趣尚待发现或细化时，可先按 [兴趣模块](../playbooks/interest-discovery.md) 展示两个具名真实体验与来源，再直接问偏好；选择后接入骨架。以下完整格式用于细化与交付，不能反过来阻塞第一份骨架。

## 主题行程的体验平衡

主题是一条贯穿旅程的选择逻辑，不是活动类型配额。内部可把正式节点理解为四种作用，但不把标签展示给用户：

- **主题锚点**：真正回应用户兴趣或旅行目的、值得专程安排的核心体验；
- **同气质的跨类型体验**：与主题共享气质、感官、文化语境或生活方式，但属于另一种活动类型；
- **沿途在地体验**：本来就在动线上的街区、景点、市场、自然、饮食、手作或公共活动，让用户真正进入目的地；
- **共同体验与留白**：让同行者都能参与、缓冲体力或保留偶遇空间。

编排规则：

- 在全程中保留清晰的兴趣重点，按用户愿意投入的时段安排，不要求每个完整游览日都有主题锚点。允许完整的独立城市体验日与休息日；相关体验与目的地本身均须有实际价值，不设固定比例。
- 多日路线主动改变形式与强度，不连续复制同一种消费、观看、拍摄或儿童项目。用户明确想天天参与同类活动时可以保留，但仍要安排身体节奏和目的地环境。
- 跨类型体验必须能说明“为什么和主题在一起”：例如咖啡连接陶器、町家、市场、庭园与晨间散步；爵士连接唱片、乐器、战后城市文化、夜间街区与安静日间；电车连接工程、城市观察、站街和交通史。
- 沿途景点不是填空。只有顺路、值得停留，并能加深主题或目的地理解时才进入正式路线；无关热门点宁可不加。
- 同行者需要轮流被照顾。亲子路线交替安排孩子能参与、成人也有兴趣及全家共同完成的体验；高刺激或明显由孩子主导的一天之后，下一段优先切换为共享、成人也真正感兴趣或更松弛的体验，避免连续堆叠主题乐园、儿童馆和儿童设施。带父母、情侣、蜜月和多代同行同样避免把一个标签复制成全天活动。
- 对用户说明平衡时按 [口语化表达](onboarding-contract.md#口语化表达与有效选择) 直接写具体安排，日程已经体现时不额外复述用户要求或重复原则；描述实际体验与节奏，不使用“一天一个重点”“每天最多一个”“至少一个”或固定比例；这些数字会把自然编排误写成产品限制。

冻结前做一次反单调检查：唱片店、爵士咖啡与音乐酒吧虽类型不同，全周都围绕它们仍然兴趣过满。如果删掉标题后，每天看起来仍是同一种店、同一种演出或同一种儿童设施的重复，就需要更换体验类型、降低某天主题强度或加入真正顺路的在地内容；不得直接用无关景点稀释主题。

## 展示顺序

完整行程按以下顺序展示：

1. 一句话说明当前路线实际包含的城市范围、移动和节奏；只有存在航班或住宿时才补抵离机场与住宿；
2. `Overview` 表格；
3. 逐日简洁时间线；
4. 行程之外的“出发前需要确认”；
5. 与同行者匹配的 `Tips`；
6. 一个具体的调整或确认问题。

用户只修改一天时，不必重贴完整 Overview；直接回显受影响当天。修改影响天数、住宿、跨城移动、体力或预算时，同步更新 Overview。

## Overview 表格

Overview 用于横向比较每天，不是把详细行程再写一遍。

固定保留：

- `日期`；
- `城市 / 区域`；用户已经要求、选择或预订酒店时才改为 `城市 / 住宿`；
- `今日安排`：只写 2–4 个核心锚点或当天主线。

航班影响首末日时，把机场写入 `今日安排` 或动态 `关键交通` 列。用户没有明确说航班已预订时，在机场或航班后标记“建议 / 待确认”；不要只写“抵达”“返程”而省略机场。

目的地内主题路线不写“抵达城市、入住”“返程”或“住宿建议”等占位内容，也不显示机场。日期未知时保留 `Day 1`–`Day N`；休馆日和周末限定项目放在“出发前需要确认”的条件式提醒中。

根据用户已经提及的关注点动态增加列，例如：

- `步数 / 体力`；
- `预计花费`；
- `关键交通`；
- `预约`；
- `雨天方案`；
- `亲子午休`。

规则：

- 最多 6 列，用户没有关心的维度不主动凑列；
- 步数、体力、花费、长途车程和预约数量等每日横向信息只在 Overview 出现一次；
- 没有可靠价格时写预算级别或“待核对”，不编造精确数字；
- `今日安排` 不复制逐日时间线；
- 体力使用统一口径，例如 `轻松 / 适中 / 偏累`，需要时再附步数区间。

示例：

| 日期 | 城市 / 住宿 | 今日安排 | 步数 / 体力 | 关键交通 |
|---|---|---|---|---|
| Day 1 | 京都 | 抵达关西机场、京都站周边 | 3,000–4,000 / 轻松 | KIX → 京都 / HARUKA |
| Day 2 | 京都 | 清水寺、东山、祇园 | 7,000–8,000 / 适中 | 上午出租车 |
| Day 3 | 大阪 | 仁和寺、跨城、心斋桥晚宴 | 5,000–6,000 / 适中 | JR 新快速 |

## 逐日简洁时间线

展开某天时按 [活动与餐饮落点](activity-classification-contract.md#具体日程的活动与餐饮落点) 查找可定位的活动与店铺；这一要求从首批具体时间线开始，不推迟到生成 Journal。

每天使用短行和简单符号，不把整天压成一个长句：

```markdown
### Day 3｜安静的京都夏日 → 大阪

- 09:00 · 仁和寺御所庭园、白书院
- 11:30 · 午餐｜<本轮已核实的具体餐厅与分店>
- 13:00 · 京都站取行李
- 13:30 · JR 新快速前往大阪
- 15:00 · 入住心斋桥附近、午休
- 18:30 · 晚餐｜<本轮已核实的具体餐厅与分店>
```

上方尖括号是模板占位，实际回复必须替换为本轮已核实的店铺，不把占位交给用户。

规则：

- 一行只表达一个时间段、地点或移动动作；
- 优先使用 `-`、`·` 和必要的 `→`，不用连续段落堆叠；
- 已安排的非例外餐饮写“午餐／晚餐／下午茶等角色＋具体店名（必要分店）”，链接到已核实店铺或地图页；不能只写片区加餐次，或“喝点东西”；便利店、赶车简餐及明确自主决定等例外按落点契约保留；
- 公园慢走、商店街逛店可保留具名地点与体验描述，位置要能检索定位；自由活动和休息同样写“在哪里＋做什么”，不能单独用自由安排占位。纯休息可依附已知住处或具名公园，不必找店；后面有固定事项时写清收尾与前往地点，不把街区活动改成收费项目；
- 博物馆、美术馆、展会和文化场馆写具体临展、常设展分区、儿童项目或准确活动名称，不只写场馆名；
- 跨城铁路、机场快线、轮渡、观光列车等核心交通，把官方预约或购票入口直接链接在服务名称上；
- Day 1 写明出发与抵达机场，最后一天写明离境机场；建议航班未由用户选择前添加“待确认”，并按供应商模板展示建议航班；有原样预订链接时放在该表格内，没有则留空，不把长链接塞进时间线；
- 开放时间、代表人背景、来源置信度、价格证据和长篇选择理由不写进时间线；
- 步数、体力和每日花费已经进入 Overview 后，不在每天末尾重复；
- 每天最多补一行极短的“节奏处理”，只说明删减或休息安排；地点和动作已写进时间线就不重复。回酒店休息须有已知住处及可入住依据，正文沿用具体住处或已说明的住宿锚点，不能用这句话掩盖地点未定。

### 简易时间契约

此时间契约从第一批具体日程就开始使用，不只用于生成请求；探索期可用上午/下午/晚上表达方向，玩法已选后立即给建议开始和结束时间，生成前补齐全程。未知抵离时首末日标为待调整窗口，不能把完整游览日当作已确认可用。估算时间对外注明为建议，固定预约与真实交通另行保留依据。

Skill 先按活动属性给每个正式节点一个可直接使用的开始、结束与停留时长，不等待真实交通：咖啡/拍照 45 分钟，寺社/书店/小型展览 60 分钟，餐饮/购物 90 分钟，博物馆/庭园 120 分钟，全天项目 480 分钟，酒店入住/退房 30 分钟，午休 60 分钟；机场、列车、演出与预约优先使用已知固定时间。POI 间可先用同场地 10、同街区 20、同片区 30、跨片区 45 分钟的常识间隔。具体事实或用户要求覆盖默认值。

每个活动写入 `schedule.startLocal`、`endLocal`、`durationMinutes`、`timingType` 与 `source: "skill_common_sense"`。`timingType` 只用 `flexible`、`fixed_start`、`fixed_range`、`full_day`、`day_anchor`；固定预约、航班、列车和已知演出不顺移。未知日期不妨碍生成这套基线时间。

日开始按用户节奏和前晚活动安排，不能晚场后仍机械默认 09:00 出门。只有已知住处时才写从酒店出发；入住从实际到店起占 30 分钟，早到只能写寄存行李，退房依据实际要求或标明建议。首末日抵离未知时展示条件式建议窗口，不编造实际交通或默认全天可用。

JourniOne 未取得真实数据前保留 Skill 时间。取得某段真实交通或营业时间后，保持 `durationMinutes` 不变，按 `ceil15(上个节点结束 + 交通 + 缓冲)` 计算下一节点；早于开门则顺延到开门，后续弹性节点同步顺延。固定节点不移动；超过关门或撞上固定节点时标记冲突，不压缩停留时长。真实数据写入 `schedule.enrichment` 的 `travelFromPreviousMinutes`、`bufferMinutes`、`openingStartLocal`、`openingEndLocal`。

## 餐饮与研究内容

餐厅、活动和交通研究仍然用于排程，但不以研究报告结构穿插在每天行程中。

正式路线的非例外餐饮时段都在时间线写出具体店铺，不因“不够有名”或用户未逐店选择就留空；暂时无可靠结果时明确该处待补，不把它说成已完成的安排。候选比较、经营背景、菜单、价格口径、预约规则、来源和限制统一放在全部行程之后的“出发前需要确认”。

用户没有要求研究过程时，每个候选最多保留：

```markdown
### 出发前需要确认

**8 月 3 日晚宴｜中国料理 大成閣**

- 适合：心斋桥附近，安静会客与少人数聚餐
- 选择：暂定 18:30、4 人、小包间
- 说明：现有公开资料显示华人经营背景；当前经营者身份仍需直接确认
- 下一步：行程交付后核对包间、套餐、价格和取消规则
```

规则：

- 只呈现会影响用户选择的结论，不展示完整研究字段；
- 来源链接落在餐厅、活动、交通名称或对应事实上；
- 重要证据存在冲突时用一句话说明，不展开调查日志；
- 用户明确要求研究报告、候选对比或来源明细时，才展开完整证据。

## 同行者 Tips

只显示与本次同行者有关的一组 Tips，不同时输出“父母、孩子、情侣”三套通用清单。每次保留 2–4 条会改变现场体验的提醒，不重复 Overview 中的步数或预算。

### 父母同行

优先提醒：

- 户外景点放在早晨，午后安排室内或回酒店休息；
- 需要爬坡、长台阶、无电梯或长时间站立的具体节点；
- 哪段建议出租车、指定席、行李转送或离洗手间近的休息点；
- 哪个节点可以随时删去而不破坏主线。

### 孩子同行

优先提醒：

- 婴儿车、电梯、洗手间、换尿布和儿童餐的真实可用性；
- 午睡、排队、炎热或雨天时可以立即切换的短方案；
- 在适合的节点保留孩子能参与的动作，不用成人景点数量衡量丰富度；
- 不把晚餐、演出或长距离移动压到孩子通常的睡眠时间。

### 情侣同行

优先提醒：

- 每天保留一个可以停留、拍照或聊天的记忆点；
- 咖啡、晚餐、夕景等约会节点要顺路，不为“浪漫”制造折返；
- 纪念日、惊喜或双人体验的预约边界；
- 不把情侣旅行排成连续打卡，主动留一段自由时间。

同行类型混合时，以行程约束更强的一方为主。例如“带父母的情侣旅行”先使用父母同行规则，再补一条适合全家的合影或晚餐提醒。

## 禁止的展示方式

- 不用一段 `09:00 → 11:30 → 13:30 → 18:30` 长句承载整天；
- 不在 Day 行程中插入餐厅所有权、公司资料、菜单调查和免责声明；
- 不在 Overview 与逐日行程中重复步数、体力、花费和交通结论；
- 不为了显得专业而展示搜索关键词、工具调用或完整研究包；
- 不在用户只关心父母同行时附加无关的亲子或情侣 Tips。
