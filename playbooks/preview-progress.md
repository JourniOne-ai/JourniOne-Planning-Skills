# Playbook: 持续更新与 Preview 交付

## 目的
用户先看到路线，逐步确认地点；提交后尽快获得 Travel Journal Preview，研究和生成期间持续看到真实更新。

## 前提条件
- 已继承当前路线、确认范围、机酒和稳定幂等键。
- Node.js 22+ 可用；正式环境默认使用 https://journione.ai；只有用户要求生成时才提交。
- 请求与响应放当前任务 .tmp，完整 Preview 不输出到公共日志。

## 步骤
1. 先交付 Overview 与首批 1–2 天；按 [活动与餐饮落点](../references/activity-classification-contract.md#具体日程的活动与餐饮落点) 查询这一批活动与实际餐饮时段的具名地点，不批量研究全周餐次与候选酒店。
2. 每确认一批，将原文、稳定活动 ID、poi/event、具体地点、服务 ID 和来源保存进当前 Snapshot；已有可靠结果直接复用。
3. 分别记录首个结果、每批研究开始/结束、冻结、HTTP 提交与接受时间。超过约 20 秒尚未完成研究时回显已完成内容和真实剩余项；不编造百分比或工具结果。
4. `node scripts/prepare-poster-request.mjs --input <输入> --key <稳定键> --output <请求>` — 本地校验地点引用、服务与请求。
5. `node scripts/submit-poster-request.mjs --request <请求> --key <原键> --output <响应>` — HTTP 提交，默认请求正式站点，每 10 秒输出实际等待时间；只有用户明确要求测试时才另传 --base；成功后把已验证响应保存到指定文件。
6. 读取成功响应并立即按交付契约返回实际 Preview 卡片；地图和图片继续由网页更新。只有明确的 QA 任务才继续等待素材终态。

## 判断标准
- 模型研究是主要的前台等待 → 优先缩小当前批次、缓存已确认事实；脚本速度不能代替规划耗时。
- 用户明确要求餐饮自行决定、便利店补给或赶车简餐等 → 可保留用餐事件；用户没有逐店选择不代表不需要推荐。普通餐饮缺店仍是当前规划缺口，已有具名活动或餐厅解析失败都如实报告，不用 event 掩盖。
- 传输断连或超时 → 脚本最多一次同请求同键重试；HTTP 4xx/5xx 不盲重试。429 保留 Retry-After，503 交给环境排查。
- 已有响应文件 → 不覆盖、不重新创建；先读取该响应核验，回到同一 Trip。

## 验证
- 模拟断连后第二次提交的请求字节和幂等键相同；非法响应不能作为 Preview 交付。
- 等待日志只有真实时间和阶段，不泄露请求正文、幂等键或 Preview。
- 环境实测记录接受耗时与素材耗时，分别报告；分批规划的桌面演练不称为真人端到端提速证据。
