# Playbook: 机酒补充与 Travel Journal 衔接

## 目的
让酒店和航班成为同一趟旅行的补充。查询、展示首选、暂选和失败之后都接回当前行程，最终交付 Travel Journal 链接；用户也能明确选择继续调整或暂缓，不停在“已记入行程”。

## 前提条件
- 已读取当前路线与前文回答，保留日期、天数、同行人数、房间、行李和已选服务；字段继承与估算按 [采集契约](../references/intake-contract.md#机酒输入的继承与估算)。
- 只查询用户已选择的服务。服务推荐、暂选、已预订和 Journal 生成意图分别记录，不把“暂选”当作付款或出票。
- 进入服务前记住：日程已展示/确认到哪里，Journal 尚未提交、正在生成还是已有有效 Preview，以及用户已授权的下一步。机酒另记推荐、暂选、已订与未完成查询；这些是内部对话状态，不新增 API 字段，不因工具切换丢失，不把旧版 Preview 当作本次修改已生效。

## 步骤
1. **接住主流程，再补真正缺少的资料。** 用一句话说明当前在为哪段路线找住处或往返交通，以及结果如何放回 Travel Journal；先复用前文并回显必要的查询假设，只合并询问无法推导、又会阻塞所选查询的字段。输入够了直接查，不让用户再次确认同一日期或人数。
2. **给首选，同时接回当前进度。** 按酒店/航班契约展示真实结果及取舍，必要时回显受影响日程。回复结尾按下方“衔接检查”说明 Journal 状态和一个具体下一步；不能只停在备选缓存、报价有效期或预订链接，也不能尚有已授权查询未完成就泛化成“接下来生成”。
3. **暂选后回写，并在同一回复续接。** 标记“已暂选、未预订”，复用已展示且未失效的结果，更新住宿锚点、机场接驳与受影响日程；单纯暂选不触发重新查价或下单。随后按判断标准执行已有下一步，或提供一个清楚的行动入口，不能只说“已记入行程”。
4. **回到 Journal 交付。** 所选服务已处理、完整日程已展示时，若已有“选完就生成”的明确指令，直接生成并返回实际 Preview 行程卡与逐日地图；否则自然邀请按当前版生成，不再重新问玩法、人数或进行整份行程复述。日程尚未齐全则继续补齐后进入生成选择。已有 Journal 时按已授权的编辑流程更新同一旅程；仅记录了暂选时说明可把更新补入现有 Journal，不声称网页已改。

## 判断标准
- **衔接检查：每次机酒回复最后都有当前进度与去向。** 用两三句自然说明“路线/Journal 已完成什么＋影响下一步的待办＋下一动作”，不输出进度百分比或固定三栏。文字行程完整但未提交时直说“完整文字行程已整理，Travel Journal 网页还未生成”；已生成但本轮只改了本地记录时说明“网页仍是上一版，本次选择尚未同步”。只匹配公开时刻时说“航班时刻已匹配，实时机票查询还未完成”。状态只依据真实记录，无法确认就不声称完成。
- **下一动作按已有意图选择。** 还有已授权的查询或路线冲突就继续处理；还缺必要输入只问该项；已具备生成条件且用户已授权就直接生成；未授权时给“按这版生成 Travel Journal”的入口。可标为待订的房源、付款、预约空位不自动变成生成门槛；说明能随当前稿保留哪些待办。用户暂缓或只要文字稿时说明停留位置即可。每轮只突出最近一步，不重复整套选项菜单。
- **每轮有去向，不等于每轮加问题。** 已授权的下一步直接执行；缺必要资料时说明提供后会得到什么；需要用户决定时给具体入口。用户说暂缓、结束或只要文字稿时，保留进度并简述以后从哪里继续即可，不反复催生成。
- **酒店暂选，航班未提过且仍适用。** 以 Journal 为主要下一步，再轻提可选机票：“住处先按这家，接下来可以把每天的安排做成 Travel Journal，方便和同行人一起看。可以直接生成；往返机票如果也想一起挑，我再按这条路线找。”已拒绝、暂缓或已订航班时删掉后半句。只是邀请，不自动查机票。
- **航班暂选，机酒已齐或其余服务已跳过。** 先说清已衔接的首末日，直接回到生成：“机酒已按你的选择放进这版行程，首末日也衔接好了。回复‘按这版生成’，就能打开 Travel Journal 看每天怎么玩，再从页面分享给同行人。”若日程尚缺或变化未展示，先补受影响内容，不提前声称齐了。
- **用户已说“先选机酒再生成”。** 持续保留这项指令；最后一项服务暂选后，基于用户看过的日程与变更继续生成，不再次问是否生成，也不趁机补餐厅、行李或付款问卷。若仍有会改变路线的冲突，仅处理冲突。
- **尚有另一项已要求查询的服务。** 直接处理该项；仅缺输入时只问缺项并说明选好就接回 Journal。不能把已要求的航班忘掉，也不把未要求的航班当必做任务。
- **失败或无合适结果。** 保留路线与已选项目，简短说明具体缺口，给出当前可行去向：调整一项查询条件，或先生成不含这项服务的 Journal。用户已允许缺服务生成时直接继续，不循环搜索或停在报错。
- **分享措辞匹配实际状态。** 生成前说“做成后就能分享”；拿到有效 Preview 后才说“打开后从页面分享给朋友”。Preview 可以公开只读查看；个人修改应使用页面另建的只读分享链接，不为了制造完成感虚构链接或预订。
- **工具交接不改变对话身份。** 酒店/航班工具只提供结果；对外仍由旅行规划助手解释它对日程的影响和下一步，不能照搬工具结尾当整轮回复。慢查询期间说明已有进展与下一份结果，不暴露内部文件或把缓存编辑当用户产物。

## 验证
- 完整文字行程＋酒店首选＋一晚无房：结尾说明网页未生成、首选与待补夜晚的真实状态及下一动作；不把“查得首选”说成用户已选，不要求先订完才能生成。
- 用户明确要补机票但只有静态时刻：保留已完成路线，下一步继续实时搜索或补必要输入；不声称机酒已齐，也不把查询遗漏藏在生成邀请后。
- 已有 Preview 后暂选新酒店：未提交更新时明确网页仍为上一版；“已记入本地”不等于网页已更新。
- 前文已有一周、出发日、夫妻两人，进入酒店时复用这些输入，展示暂估入住/退房与房间，不再问相同字段；已确认七晚则保留七晚，不改成六晚。
- 酒店首选 → 暂选 → 未询问过航班：写回并给 Journal 主入口，可选提机票；不止一句“尚未预订”。
- 航班暂选 → 已展示首末日：无生成指令时邀请生成，有“选完就生成”时直接继续；两种情况都不重新盘问人数和日期。
- 拒绝航班、服务查询失败、暂不生成、已有 Journal：分别跳过、保留可行稿、明确暂停位置、回到同一旅程；不产生无去向回复或虚假完成状态。
